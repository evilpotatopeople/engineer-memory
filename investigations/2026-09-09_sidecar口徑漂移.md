# derived artifact 口徑漂移靜默走鐘 — /investigate
日期：2026-09-09
Skill：/investigate
狀態：已結案（機制已修 + 回歸測試 + 稽核腳本；11 支既有不一致 config 待決）

## 摘要（一句話）

cohort 產的 sidecar（`grid_json` / `pace_profile.json`）沒記錄自己是在哪組口徑下算的，
consumer 讀到不同口徑的 sidecar 時 join key 照樣對得上、覆蓋率照樣綠燈，數字卻錯 28%。

## 症狀

ladyn TW 秋寵 2026 事前預估：planner grid join 覆蓋率 100%→99%（miss 335 客）印綠色 ✓，
但營收中標從 1,997,384 掉到 1,429,276（−28%）。

## Root cause

planner 把「自己從 CSV 現算的 current_grid」跟「cohort 先前產、存在 sidecar 的 ref grid」
對接，join key 是 RFM 桶的**標籤字串** `(r, m, f)`。

config 分兩類：

- **label-space**（`R_BUCKETS` / `M_BUCKETS` / `F_BUCKETS`）：改了 → 標籤字串變 →
  join 全 miss → 覆蓋率塌到接近 0 → 既有守門（planner `analyze.py` P0-2、2026-06-11
  為 HK 桶不對齊全 0 事故加的、閾值 `cov < 0.5`）會大聲叫。**有覆蓋。**
- **membership-space**（`EXCLUDE_ZERO_TOTAL_ORDERS` / `INCLUDE_ANONYMOUS_AS_NEW` /
  `ACTIVE_WINDOW_MONTHS` / `M_LOOKBACK_MONTHS`）：改了 → **標籤一個字都沒變**、只是誰
  落在哪一格變了。**沒有覆蓋。**

ladyn TW 實測（同一份 CSV、兩種口徑）：

```
客戶數      含$0 41,893  →  排$0 41,858    （只少 35 人）
label 集合  467 格 vs 414 格、交集 366 格
共同客戶    41,858 人，其中 4,508 人換了格子 = 10.8%
```

所以錯的**不是 join miss，是 join 成功但配到錯的係數**——那 10.8% 的人 join 都成功，
只是拿到用另一種口徑算出來的 recall rate 和 avg_spend。miss 的 335 客只是副作用
（149 個只存在單邊的稀疏格）。覆蓋率這個指標（按客數算）在設計上就量不到這種錯。

**觸發時序**：`EXCLUDE_ZERO_TOTAL_ORDERS = True` 在 2026-09-09 11:19 隨品牌字典 D 段
（commit 1dae6bf）加進 `ladyn_tw/hk_cohort.py`，但 reference 的 grid_json 是同日 10:34
產的。config 改了、cohort 沒重跑，系統完全不知道。

跟 2026-08-07 的 `fixed-sleep-grep-race` 同一個家族：**silent-fail——失敗時吐出一個看
起來合理的數字，而不是報錯。**

## 結構上沒覆蓋到的（調查發現）

1. **sidecar 零 provenance**：`grid_json` 的 `schema` 就是字串 `"grid.v1"`；
   `pace_profile.json` 連 `schema` 都沒有，但它存的 `campaign_total_orders`、
   `share_of_campaign` 都是口徑相依的。
2. **沒有 staleness 檢查**：沒有任何地方比對 sidecar 產生時間 vs config 修改時間。
3. **7 個影響格子語意的旗標，只有 3 個（label-space）會被既有守門抓到。**
4. **planner config 與 cohort config 各自獨立宣告口徑、靠人工抄**：稽核掃出 11 支
   planner config 跟它的 cohort config 不一致（ladyn 6、heromama 5、lm 0——lm 兩邊都
   沒開旗標所以一致）。這些是**潛伏**的：過去產出當時是一致的，誰重跑就中。
   `heromama_tw_plan_lunar2027` 是未來檔期、一定會被重跑。
5. **讀 sidecar 的不只 planner**：`dtc-promo-analyzer`、`dtc-campaign-report`、
   `_shared/offer_behavior.py`、`_shared/monitor.py`、`_shared/midflight_check.py` 共 7 個
   consumer 共用同一個假設。
6. **`validate_cohort_index_alignment`（`_shared/brand_calendar.py:137`）只比對檔期窗口**
   （cohort `CAMPAIGNS` vs campaign-index 的 name/period），不碰口徑、不碰 artifact 新舊。

## 修法（已落地）

新增 `_shared/caliber_fingerprint.py`：把 7 個口徑欄位序列化成 12 碼指紋。

- cohort 寫 sidecar 時 stamp 進去（`grid.v1` → `grid.v2`、pace 新增 `pace.v2`）
- consumer 讀時比對，不一致 → **hard fail 並逐欄指名差在哪**（`--skip-validate` 可繞過）
- 舊檔（無 caliber block）→ 警告但不擋，不假裝一致
- 新增口徑旗標只要加進 `CALIBER_FIELDS`，7 個 consumer 自動受保護

配套：

- `_shared/qa/test_caliber_fingerprint.py` 10 個 case、註冊為 `run_checks.sh` 9/9
  （突變測試驗證過：把 `EXCLUDE_ZERO_TOTAL_ORDERS` 從 `CALIBER_FIELDS` 拿掉 → 測試紅）
- `_shared/audit_caliber_alignment.py` 一次掃全部 planner config × cohort config +
  全部 sidecar，exit 0/1/2

## 證據

- 重現事故（planner 口徑改回 False vs grid=True）→ 守門觸發、exit 1、指名
  `EXCLUDE_ZERO_TOTAL_ORDERS: sidecar=True vs 當前=False`
- 正常路徑 → 靜默通過、TW 中標 1,997,384 / HK 144,462 與修復前一致
- `./run_checks.sh` 9/9 全過（含 golden 回歸 cohort→promo→planner 三段鏈）
- schema v2 向後相容：全 repo 無任何 consumer 硬檢查 `schema == 'grid.v1'`
