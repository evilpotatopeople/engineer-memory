## 摘要（一句話）
想做的「分析任務建檔＋標籤」，實測後發現真正的問題不是重複造輪（規模只有贈品 3 份定義），而是產出跟口徑版本沒綁定；解法是把 9/9 已經做好但 0/17 使用率的 `caliber_fingerprint.stamp()` 接到分析產出上，標籤軸＝口徑 id、不用人工標。

## 本次最重要的教訓：我的第一版診斷全錯
第一版拿**關鍵字出現次數**當「重複實作」的偵測器，得出「贈品重寫 7 次、is_warehouse 重寫 4 次且 0 import」，據此推薦「口徑止血 + lint 擋門」。獨立對抗性審查（品質分 4/10、15 條問題）抓出來，逐條複驗後確認：

| 第一版宣稱 | 複驗實測（2026-09-21） |
|---|---|
| 贈品判定重寫 7 支 | **2 支**有真邏輯，其餘 5 支是 HTML 報表文案；且 mzyx 那組用的是 `行金額 > 0`，解不同問題 |
| `is_warehouse` 重寫 4 支、0 import | **0 支重寫**。4 支全是讀 DuckDB view 欄位（`is_warehouse_line` / `v_warehouse_orders`） |
| `_shared` 沒有贈品共用模組 | **有**，`warehouse_keywords.json` 逐品牌存 `gift_lines`（10 處） |
| `Total>0` 5 支 / 引用 `_shared` 12 支 / import 共用模組 2 支 | 8 支 / 11 支 / 3 支 |

**結論反轉**：口徑重用一直在運作，管道不是 Python import，而是把口徑**物化進 DuckDB view** + `_shared.campaign_review` 引擎。「有庫但沒人用」不成立。

## 實際確認存在的三個問題
1. 贈品定義有 3 份（`gift_lines` + `build_ladyn_box_day1_gap.py:82` + `build_ladyn_consignment_tiers.py:58`）。小。
2. **下游 override 會過期、沒人發現**。`build_ladyn_box_day1_gap.py:9-11` 的 docstring 還寫「不直接用 `decompose.is_wh_order`，因為引擎把券碼含『寄倉』的也算」——但上游同日（2026-09-15）已修，`decompose.py:128` 的 `_WH_COUPON_NEG = ('不適用','不包含',…)` 就是那次修法。兩邊今天一致，未來各自漂移。
3. 226 個 `pbi_query` DAX、72 份 HTML、39 份 research，沒有一份記得住自己用哪個版本口徑算的。`caliber_fingerprint.py` 的 `stamp()`/`verify()` 目前 **0/17** 支分析腳本使用。

問題 2 與 3 是同一件事：產出跟口徑版本沒綁定。不是「重複造輪」，是「回溯不了」。

## 定案
**Approach A — 產出蓋口徑指紋**，只切最窄一刀：只對新寫的分析腳本蓋，不回補 226 個舊檔。
- 標籤不用人工標，是執行時記的；標籤軸＝口徑 id（使用者自己點出「標籤要設計好才行」，這是答案）
- 口徑 id 用裸名 `gift` / `deal` / `warehouse`，第一期三條
- 分發：`_shared/caliber_fingerprint.py` 既有 API + 工作目錄 `CLAUDE.md` 一行
- **「掛 run_checks」已確認不可行**：`run_checks.sh` 屬 `dtc-campaign-analytics`、開頭 `cd` 回自己的根；`~/Desktop/Claude test` 的 `.git/hooks/` 非 sample hook 數 = 0；臨時分析腳本常跑完交報表就不 commit
- 已否決：只收斂贈品 3 份（太小）、停手（226 DAX 一週長 5 個，會更貴）
