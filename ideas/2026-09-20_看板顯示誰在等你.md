# 看板顯示「現在有幾個視窗在等你回話」 — /office-hours
日期：2026-09-20
Skill：/office-hours
狀態：進行中（已建檔成 agent-ledger T-0099，帶三個階段子任務）

## 摘要（一句話）
AI 停下來等人回答時主動回報到 agent-ledger 看板，不必人去巡每個視窗；技術上兩家都接得到，**但今天查到的全是文件、一項都沒實跑驗證過**，所以第一步是 spike 不是動工。

## 詳細內容

### 使用者原話
「dashboard 裡面理論上 AI 運作到需要人回答時會停下來，目前是我人類需要去每一個窗口檢查是否需要我操作，那這東西是否有機會可以回傳到 dashboard 上，然後顯示在上面，讓我統一管理，更方便推進任務」

### 拷問後拍板的四件事
1. **要即時狀態、不要累積清單**——「現在這一秒有 3 個在等我」，不是「今天卡了 7 次」。理由：需要他推進、不然任務不會往下走。
2. **Claude 與 Codex 兩邊都要收**。
3. **Codex 第一階段只收得到「跑完一輪」**、收不到「等你按允許」，接受。
4. **假警報一天一兩次可接受**。不對稱性：假警報的代價是多點一下；漏報的代價是任務整晚卡著沒人推。寧可寬鬆多報。之後分階段做準。

### 技術事實（2026-09-20 查證，來源＝官方文件＋本機 config，非實跑）
| 停頓情境 | Claude Code | Codex |
|---|---|---|
| 跑完一輪、球回人手上 | `agent_completed` / `Stop` | `agent-turn-complete` |
| 卡在「要你按允許」 | `permission_prompt` | ✗ 只在 `[tui]` 內，外部程式收不到 |
| 閒置等你打字 | `idle_prompt` | ✗ |
| 跳對話框問你 | `elicitation_dialog` | ✗ |
| 人回話了（用來清卡片） | `UserPromptSubmit` | ✗ **沒有對等事件** |

Notification hook 共同欄位：`session_id`、`transcript_path`、`cwd`、`permission_mode`。

### 三個非顯而易見的發現
1. **主要工程在看板端、不在 hook 端。** 現況 `scan` 由 launchd 每 600 秒跑、`board.html` 每 120 秒重整 → 最差 12 分鐘才看得到，而使用者要「這一秒」。好消息：實測 `hand scan` 一次只要 **1.19 秒**，hook 可以直接踢它、不必等那班車。剩下的延遲只剩 board.html 的 120 秒 ＋ 1.4MB 整頁重載。候選解＝做一個只有「在等你」那一塊的獨立小頁（幾 KB、refresh 短），大看板維持 120 秒，不動 CSP `default-src 'none'` 的單檔靜態設計。
2. **Codex 的 `notify` 是單一格子、不是清單，而且已經被佔用。** 使用者 `config.toml` 那一格是 Codex Computer Use 的 `SkyComputerUseClient turn-ended`。要加只能寫 wrapper 轉發——**包壞了 computer use 通知會默默消失、不報錯**（silent-fail 家族的典型形狀）。
3. **Codex 標得起來、清不掉。** 只有「我跑完了」、沒有「使用者回話了」，看板會長殭屍。解法候選＝不只信事件，配合對話檔 mtime：turn-complete 記下時間 T，`scan` 時看該 session 的 JSONL 有沒有在 T 之後又被寫過，有就是人已回話、自動清掉。Claude 端同樣適用（`transcript_path`），而 `scan` 本來就在掃那兩個資料夾，成本近乎零。

### 已經現成、不用重做的零件
- hook 給的 `session_id` 就是 `cliSessionId`，而 `scan` 已經在逐檔算雜湊把它對回 `local_<uuid>`（411 個 session 檔、9/20 實測 90ms）。**「在等你」卡片上的「開對話」按鈕不用另外做**，點下去直接跳回那個卡住的視窗。
- Codex sandbox 的 `writable_roots` 已含 `agent-ledger/data`（9/19 標的兩大風險之一，已解）。

### 最大風險（未解）
今天所有結論都來自官方文件與本機 config，**沒有一項是實際跑出來驗證的**。`ideas/2026-09-19_跨agent交接帳本.md` 當時就把「桌面 App 吃不吃 hooks」列為開工前要 spike 的最大風險，至今沒驗。整個構想壓在這個假設上。
